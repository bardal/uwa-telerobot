World Wide Web Telerobot: Task Performance Measurements

Authors: Kenneth Taylor and Associate Professor James Trevelyan.

Abstract

We have built an experimental World Wide Web based Telerobot whose address is http://telerobot.mech.uwa.edu.au/ and are investigating the potential of this technique. It is envisaged machinery can be made available to many users by this method however the advantages of teleoperation are balanced against the disadvantages associated with the longer times required to accomplish tasks. With a desire to decrease task times a method is needed to quantify task performance and predict the effects of particular changes to the process. Several methods for measuring telerobot performance are considered but they do not by themselves provide a framework for predicting the effects of changes. A simple model is developed to provide the necessary framework for an investigation of task times. Using the definition of Sheridan and Ferrell the model is of the functional type where it is to be used to predict consequences of design changes on system performance as distinct from the structural which postulates causal mechanisms. The techniques are applicable to the control of any world wide web based device or a telerobot which uses a similar supervisory control paradigm.

 

We have applied the model to the UWA Telerobot installation for the task of stacking blocks. The reductions that are achievable with differing techniques are predicted. For block stacking, no methods are envisaged that will bring the times close to that achievable by manual handling. Estimated task times are important when comparing this method of teleoperation with other common methods and when considering the suitability of teleoperation for particular applications.

The robot server consists of a 486-PC which runs a Web server program running under a Windows 3.11 operating system. Measuring Teleoperation Performance

 

The time taken to complete a manipulation type task is invariably greater in teleoperated systems than with manual handling. Balanced against this is the advantages of making machinery available to a large number of people who do not have to be in the same place as the machinery. Therefore techniques and methods for improving speed and performance are important. The success of the techniques requires an understanding of what represents performance and a method for measuring it. The obvious definition of performance is how long does it take to complete a given task but there are other possibilities. Methods available for measuring performance are:-

 

(i) Time to complete a task. This is the common method that researchers [,,,,,] use to measure system performance and provide comparisons between systems. It requires a controlled experiment where a number of operators perform the same task. The experimenter then varies either an aspect of the task or an aspect of the interface asks operators to repeat the task. It works well in a controlled laboratory environment but can not be used to monitor ongoing system performance as operators will be performing varying tasks.

(iii) Operator Subjective Assessment. McClean[] et. al. found this was closely correlated to the more generally used time to complete a task. Operators are asked to complete a task as quickly as possible and then rate the task in comparison to a separate baseline task which doesnt involve teleoperation. The baseline task is to manipulate graphic objects with a mouse and its baseline task minmimises variability between operators.

 

(iv) Average joint velocity. The period over which the velocity is averaged is the entire session for an operator. The rationale for this is that good operation will consist of purposeful motions therefore the more movement the better. It has the advantage that no defined task is required, it being possible to acquire the data while the telerobot is in general use. It offers no predictive value though, in that the effect of a change can not be predicted prior to its implementation. It was proposed by McClean[] et. al. It is fairly closely correlated to the time to complete a task.

 

(v) Average tip velocity. This is proposed by McClean[] et. al. and is based on the same rationale as (iv) but the measure is in cartesian space rather than joint space. It was found to give very similar results to (iv).

 

(vi) Dexterity. This is another measure proposed and tested by McClean[] et. al. which is based on the assumption that good performance is associated with the manipulator being maintained in a state from which a variety of motions can be easily achieved. That is that the manipulator is best operated away from singularities near which high ratios of joint rate to task velocities are achieved. The dexterity is based on the determinant of the Jacobiean. This measure of performance was found by McClean[] to be less well correlated to time to complete a task than the methods discussed in (iv) and (v).

 

(vii) Sum of squares of the contact forces(SSOF). This measure is used by Uebel[] et. al. when assessing the effect of bandwidth on a peg insertion task. (viii) Sum of the squares of the moments. This measure is similar to that described in (vii) but the moments applied to a peg during a peg insertion task are measured rather than the axial forces. It was used Uebel[] et. al. with similar results to that described for method (vii) and also by Hannaford and Wood[].

 

The applicability of each of these techniques to the UWA telerobot installation is:-

 

(i) Time to complete a task. This is very suitable for structured experiments.

 

(ii) Fitts Law. This model is restricted to manipulative tasks on which the theory is based and systems where a human is performing rate and position control with constant and short communication delays. In this telerobot system an operator specifies a target rather than controlling rates of movement the local control system moves the robot at arbitrary speed to the target so clearly the model does not apply to this system.

 

(iii) Operator Subjective Assessment. This is the technique used to guide most of the development of the interface thus far but the assessment has not been quantified and the comparison has been between different forms of interface rather than a base line task.

 

(iv) Average joint velocity. This would be very useful in our installation which receives a lot of use from many operators who all have different goals and whose goals are unknown. It cant be used to predict the effect of a change prior to its implementation.

 

(v) Average tip velocity. The applicability is similar to (iv).

 

(vi) Dexterity. It was found by McClean[] to be less well correlated to time to complete a task than other methods and is likely to be less useful in the case of the UWA telerobot due to a lower operator awareness of joint positions than in McCleans[] installation.

 

(vii) Sum of squares of the contact forces(SSOF). The technique is limited to tasks of the peg in hole type. It is not suitable for the method of teleoperation employed by the UWA telerobot installation as the operator specifies goals and interaction with the environment is entirely under machine control.

 

(viii) Sum of the squares of the moments. As for method (vii) it is not suitable with our method of teleoperation.

 

With a desire to model the robot operation and predict ways it could be improved a time to task completion is used in this case.

Model Of Telerobot/Operator System

When an operator attempts to achieve a goal there will be a number of subgoals required. The number will not be the same for all operators. The operator is usually developing the strategy while pursuing the goal therefore the number of subgoals will not generally be known when beginning a task. However for a given strategy there will be a fixed number of subgoals providing that each subgoal is successful and there are no unintended consequences of achieving each subgoal. An example of an unintended consequence would be to knock over an existing block structure. A strategy is assumed to be the same regardless of whether teleoperation or local control is used.

Applying Values To The VariablesCalibrating Model

 

Having defined a model values for each of the variables are required. Each variable will have a probability density function but for the purpose of predicting overall task times mean values are sufficient. The aim is to provide an estimate of achievable times for a particular task and to estimate the effect of various possible modifications. The data can also be used to estimate task times for other types of tasks using teleoperation with a World Wide Web interface. Some of the variables will have very different values depending on circumstances, the most obvious of these being communication time, which depends on the bandwidth available to each operator. The data rate to the United States from the University of Western Australia depends on the time of day and the network quality which changes remarkably from week to week. Sometimes data rates averaging 200 bytes a sec are achieved and other times 25 kilobyte per second. Therefore the values will be imprecise. However predicting the effect of system modifications does not require high precision.

 

- Time required to generate response and communicate with robot. With a single request to the server the time is variable. This is measured by specifying a zero movement to the robot with default settings of 256 x 256 pixel images and 16 grey scales. A sample of 9 gave a mean of 11.3 seconds and a standard deviation of 1.1 seconds. If there are multiple users accessing the server this can be increased. It was 16 seconds with one other user requesting files from the server simultaneously. A large proportion of the time is consumed in acquiring and compressing the camera images. The time taken to acquire two images compress them and generate the HTML document again with default image settings averaged 8.5 seconds with a sample of 7 and a standard deviation of 0.7 seconds. This can be considerably reduced with an improved frame grabber and a more powerful computer.

 

- Time taken for robot to achieve a subgoal. The possible subgoals are operate the gripper or move to a location. The gripper will take 1 second to operate and the robot can move at 100 millimetres per second. It has been restricted to this to avoid damage when it is brought into contact with a fixed object. The acceleration and deceleration time is negligible for these speeds. The gripper is restricted in software to positions within an imaginary cube with sides of length 600 mm. Assuming the gripper is operated on every third move, a change in orientation adds one second every third move and a mean move interval of 230 mm. An estimate of the mean time taken is 3 seconds.

 

- Communication time. This is dependent on the communications bandwidth, the round trip delay and the speed with which an operators computer can decode and display the incoming data, particularly images. For many the slowest part is the telephone link from the internet access provider to the operator. It is also dependent on the amount of data to be transmitted. With standard settings and excluding the image supplied from Germany the data transmitted is:-

(i) 7.5K kilobytes for each of two camera images based on a sample of 345 images with a standard deviation of 1.0K. kilobyte

(ii) 4.6K kilobytes for a wire frame model with 0.2K kilobytes standard deviation based on a sample size of 540 images.

(iii) 2.8K kilobytes of text.

(iv) An overhead of approximately 12% associated with transmission protocols.

 

This gives a total of 25.1K kilobytes. Assuming a transmission speed of 2.5K kilobytes per second and a decoding time of one second a value of 11 seconds can be estimated. Operators can also select options which will increase or decrease the amount of data to be transmitted. To communicate and display the information on a 486 PC connected by an ethernet local area network takes about 6 seconds.

 

- Operator decision making time. This is hard to measure as it is particularly difficult to separate communication time from operator decision making time. We have observed large differences between operators and decreases in time with practice. It has also become apparent as the interface design has evolved that the interface designvaries for every subgoal depending on cognitive effort required to specify the goal and alters this significantly. It varies for every move alsothe cognitive effort is partly dependant on interface design.

Considering each of these options:-

 

Shorten time required to generate response and communicate with robot ().

This is long, more than a quarter of the total time per subgoal. Reducing it to requires an engineering effort but does not require innovation. Strategies which could be adopted include, optimising the code, using a more powerful processor, using parallel processors. For example using a second networked computer to capture the images with the robot triggering the image acquisition at the end of its move sequence. and supplying them from this source. Goldberg achieved a turn around from move to move of five to ten seconds for his raiders robot operated from a browser on the same ethernet network which implies only a few seconds required for this task. A modest engineering effort should be able to achieve two seconds. This would reduce the time for the standard task by 3 minutes and 10 seconds.

 

 

Shorten time taken for robot to achieve a subgoal ().

 

At three seconds this represents 7% of the cycle time. The robot moves slowly to avoid risk of damage. The speed could be increased significantly whenever the robot was not moving towards the table. Gripper time can not easily be changed. This would perhaps halve the average movement time to 1.5 seconds. This would reduce the standard task time by 28 seconds.

 

Shorten communication time ().

 

Multimedia capabilities of computers are increasing at a dramatic rate and in the longer term the bandwidth of the internet will increase. This can perhaps be expected to halve within a few years. Eighty eight percent of the data is associated with image transmission. Currently a java script is being developed which will generate the wire frame model on the users computer rather than transmitting an image. This will reduce the 4.6K kilobytes to about 100 bytes and with the viewing angle being able to be changed by the operator interactively will convey much more information. Assuming a transmission speed of 2.5K kilobytes per second this will reduce the transmission time per subgoal by 2 seconds. The standard task time would be reduced by 38 seconds. Reducing image size will reduce the data content considerably. With clickable images it also reduces the resolution of the position that can be selected. The standard size gives a resolution of about 5 millimetres per pixel in the centre of the table. New images are only required when the operator alters the environment and not every move will do this apart from repositioning the robot. Operators can currently select not to update an image but this is rarely done. A change in the interface design could encourage this strategy. For the standard task, if images were updated only after placing each block 7.4 seconds could be saved on 16 of the 19 subgoal requests resulting in a saving in 1 minute 68 seconds for the task. One change which might encourage operators to adopt this strategy is updating each image alternatively unless an operator requests both to be updated. This would reduce the standard task time by 1 minute and 10 seconds.

 

Using jpeg coding rather than gif can lessen the amount of data per image but jpeg images take longer to compress and to decompress at the operators site. While compression times can be made small with a more powerful processor whether there is an overall gain in speed depends on the speed of the operators computer in decoding and the transmission rate. As multi media capabilities of computers increase it can be expected decoding times will be insignificant in the future and transmission times will be the overriding consideration. Large areas of a single colour are coded well by the gif method. Using the usual jpeg quality setting of 75% and with only sixteen shades of grey and a large proportion of the background being a single colour similar amounts of data are required with either coding scheme and jpeg can sometimes be larger. A sample of five images coded by both methods produced a mean saving of only 2% for jpeg encoding. However if higher quality jpeg images or colour were provided a significant advantage could be expected also by accepting lower quality images data can be reduced by more than half.

 

Shorten the operator decision making time ().

This can be achieved by increasing the quality of the feedback to operators. Often this will require increased data to be transmitted to the operator so there is sometimes a trade off with communication time. It is apparent that the layout of the interface is important. Operators currently have difficulty in interpreting the wire frame images, and in relating block position data to this image and images to the coordinate data. The vast majority of current operators are very inexperienced so a lot of operator decision making time is directed to understanding the interface. The java interface will show robot position and allow the wire frame model to be dragged around the screen a cross will move to the corresponding location in each of the two camera images. This is likely to be more intuitive and encourage a higher percentage of users to use graphical instructions rather than typing position data. The camera views are currently orthogonal. It can be difficult to identify the same locations in two views and it may be more intuitive to mount the cameras with some other angle between them. A view from the robot gripper may impart more information also. For a human attempting this task with one arm the quality of the visual and other sensory feedback is sufficient to reduce decision making time isto very close to zero. This level is not likely to be achievable with a screen but reducing it to 5 seconds seems reasonable.

Lessen the number of unsuccessful subgoals

This can be done by making it apparent to an operator subgoals that can not be achieved. For our application the local simulation, possible with a java interface, can eliminate subgoals outside the joint space of the robot by the simulated robot failing to move to these poses. Ensure there are no unintended consequences

This requires that all possible effects of a move be considered and strategies developed to counter them. This is the principle difficulty of full automation as the number of things to be considered can be very large and developing a strategy for each can be very time consuming. It is the lack of a requirement to do this that makes supervisory control an attractive strategy. As well the methods developed are likely to be specific to a particular task.

 

For block stacking this requires recognising the existence of a stack probably by image analysis and planning a path for every point on the robot that will not intersect the stack space. It is probably better to rely on an operators ability to avoid this.

Combining Options

 

A strategy of using a java interface which will allow an overlap of operator decision making times with other times, eliminate unsuccessful subgoals, remove the requirement for wire frame image transmission. As well as shortening feedback time f to 2 seconds, subgoal time s to 1.5 seconds, image updates only after placing each block, an operator decision making time o of 5 seconds. The standard task would then take 2 minutes and 25 seconds a saving of 11 minutes and 50 seconds.

Conclusion

 

A model has been presented which is useful for analysing a telerobotic task and predicting the effects of applying different telerobotic methods on the time it takes to complete a task. The model has been applied to the task of stacking three blocks using a telerobot we have built. The effect of different changes to the process on task times has been investigated. The model predicts large improvements are possible by implementing a combination of changes to the telerobot and its interface, reducing the time taken for this task to about 20% of the time currently required.

 

The model is applied to a human performing the task without a robot. This is compared to what might be achievable by increasing the efficiency of telerobotic operation and a human performing the task of block stacking. It is apparent that the task could never be completed using telerobotic methods in the time a human alone could complete the task. The more automated the task the smaller the additional time associated with teleoperation is as a proportion of the total task time. The classes of tasks for which telerobotics with this technique are likely to be suitable are:-

(i) Environments inhospitable to humans including space, undersea and underground mining.

(ii) Tasks requiring forces greater than a human can achieve e.g. machining with the robot holding a tool.

(iii) Tasks requiring greater precision in movements than a human can achieve.

(iv) As a means of sharing equipment among many users, for example sign writing or engraving equipment.

(v) Entertainment.
